# Cutover boundary

Status: **no system has been cut over to VSC.** Existing Pask owners remain authoritative for school, deadlines, mail/calendar, contact, compute and Beer.

## Preconditions for any cutover

1. Durable VSM kernel with one root, legal organs/channels, grants, purpose comparator and constitution checks.
2. Native execution adapter qualified in a disposable Gateway: accepted receipt, lost-reply ambiguity, restart recovery, cancellation/drain and duplicate-completion tests.
3. One closed homeostat with an independently read-back effect and alarm path.
4. Accountable evidence: canonical episodic references, effect intents/outcomes and bitemporal state; no private bodies in public projections.
5. Audit, algedonic and purpose feedback loops exercised on synthetic disturbances.
6. A predeclared canary purpose with an existing owner, source of truth, acceptable bounds and rollback.
7. Exactly one executor for each obligation during migration; no double execution.

## Migration sequence

1. **Shadow:** VSC observes the existing owner and produces evidence/alarms without acting. Compare against the owner's receipts.
2. **Canary:** one reversible, read-only or low-risk obligation; VSC acts only within a narrow grant; the existing owner remains able to stop it.
3. **Supervised handoff:** VSC owns the obligation, old owner becomes a backstop for a fixed window; every effect is read back.
4. **Atomic cutover:** disable the old executor only after the replacement has passed restart, ambiguity and rollback tests. One live owner.
5. **Post-cutover audit:** compare outcomes, latency, false alarms and cost; roll back on unexplained residual.

## Never

- Do not migrate by editing programs.yaml or automations first and hoping the runtime catches up.
- Do not let a bound session rewrite its own grants.
- Do not treat a graph binding as ownership transfer.
- Do not claim a day of operation from a synthetic test.
